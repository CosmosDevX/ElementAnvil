# Что проверено в Элемент Скрипте 10.0.4

Проверено на установленном комплекте `1c-enterprise-element-script-10.0.4+21-x86_64` и Java OpenJDK 17.0.20.1. Выводы относятся к этой локальной версии отдельного Скрипта, а не ко всем окружениям полной платформы Элемента.

## Слои исполнения

Редактор поставляется на Theia/Electron. Языковой сервер, компилятор и исполнение — отдельные Java-компоненты. Launcher `executor.cmd` выбирает Java из `JAVA_HOME`, затем PATH, добавляет `executor/lib/*` в classpath и запускает `com.e1c.g5rt.executor.boot.ExecutorBootstrap`.

В `com.e1c.g5rt.xbsl.engine` обнаружены собственные представления модулей и методов (`MethodImage`), стековые кадры (`BslStackFrame`), стек операндов и указатель команды `cmdPtr`. Байткод метода `BslStackFrame.runTo()` содержит цикл `commandsProxy.getCommand(cmdPtr)` → `exec(command)`.

Это конкретное свидетельство интерпретации внутренних команд Элемента внутри Java-движка. Наличие JVM не означает, что каждый `.sbsl` прямо превращается в обычный Java-класс. JIT JVM может оптимизировать Java-код самого движка; собственный JIT для команд Элемента в этом исследовании не подтверждён.

Стандартные типы соединяются с движком через обёртки. Например, `TcpBlockingServerBslImpl` создаёт `TcpBlockingServer`, запускает его и регистрирует как ресурс текущего `IBslProcess`. Реализация TCP использует `java.net.ServerSocket`, однопоточный `ExecutorService` и блокирующий `Future.get()`. Внутренний Java-поток сам по себе не даёт асинхронного API скрипту.

## Сборщик мусора

Launcher не задаёт GC явно. На отдельном реально запущенном `.sbsl` команды `jcmd <PID> VM.flags` и `jcmd <PID> GC.heap_info` подтвердили:

```text
-XX:+UseG1GC
-XX:G1HeapRegionSize=2097152
-XX:InitialHeapSize=266338304
-XX:MaxHeapSize=4253024256
garbage-first heap
region size 2048K
```

Это G1 из HotSpot. Размер региона, начальная и максимальная куча выбраны JVM под данное окружение и могут отличаться на другом компьютере или с другими флагами. Максимум кучи не означает, что процесс сразу занимает всю эту память. Metaspace, код JIT, стеки потоков и другие области находятся вне Java heap.

G1 делит кучу на регионы, различает молодые и старые объекты, часть работы выполняет параллельно приложению и всё равно имеет паузы. В этой Java `MaxGCPauseMillis=200` — целевой ориентир, а не обещание максимальной паузы. [Документация G1 для Java 17](https://docs.oracle.com/en/java/javase/17/gctuning/garbage-first-g1-garbage-collector1.html).

## Что можно исследовать и менять

- `javap -p -c -classpath <JAR> <полное имя класса>` — сигнатуры, приватные поля, байткод; декомпилятор может восстановить приближённый Java-код без исходных комментариев.
- `jcmd <PID> VM.flags`, `GC.heap_info`, `Thread.print` — настройки JVM, куча и стеки. `JFR.start` позволяет записать профиль CPU, аллокаций и событий GC. [Справочник jcmd](https://docs.oracle.com/en/java/javase/17/docs/specs/man/jcmd.html).
- Через параметры именно процесса Java можно менять `-Xms`, `-Xmx`, включать `-Xlog:gc*`, выбирать другой доступный GC. Наличие опции в JVM не подтверждает совместимость конкретного комплекта Элемента с любой другой версией Java или конфигурацией.
- Java-агент может инструментировать загруженные Java-классы. Экспериментальная замена класса или JAR технически возможна в отдельной копии runtime, но это зависимость от внутренних интерфейсов, а не штатный публичный плагин.
- Для нового типа, доступного из `.sbsl`, недостаточно положить произвольный JAR в classpath: нужен мост к системе типов и регистрации окружения Элемента.
- Для экспериментальной асинхронности понадобятся доступные скрипту операции задач/готовности и согласование с контекстом `BslProcess`. Потокобезопасность произвольных обработчиков и объектов Элемента в нескольких Java-потоках не установлена. Простая подмена `accept()` не добавит `async/await` в язык.

Установленные файлы Элемента не модифицировались. Диагностический скрипт запускался отдельно и после измерения был остановлен.
